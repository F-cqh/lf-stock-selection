## 一、为什么做这个

现在 `D:\选股` 里的东西是一堆**脚本**：`run_strategy.py` 抓数据 → 跑 instock 的 9 个策略 → 写 `result_strategy.csv`。能用，但有三个硬伤：

1. **只能选股，不能验证**。输出是"命中了 37 只"，但没有"如果按这个策略交易，8 年能赚多少、最大回撤多少"。
2. **没有防未来函数的能力**。这是量化新手回测虚高的头号原因，而且不专门设计就一定会踩。
3. **数据层和策略层耦合**。换数据源要改策略，加一个策略要复制一遍抓取逻辑。

**目标**：造一个自己的、能长期迭代的 A 股日线回测研究平台。核心是一台可信的回测引擎 + 一个浏览器里看的界面。不碰实盘，先把"策略到底行不行"这件事做扎实。

**已确认的边界**

| 项 | 决定 |
|---|---|
| 市场 | 沪深主板约 3100 只 |
| 区间 | 2018 至今，约 8 年 |
| 颗粒度 | 日线 |
| 用途 | **低频选股交易**（月频/周频调仓，持有几十只） |
| 界面 | Web（浏览器） |
| 代码 | 全新仓库，现有代码只做参考不迁移 |

### 1.1 两个前置事实（探索现有代码时发现的）

**① instock 里的 `core/backtest/` 不是回测**

它只有一个函数 `get_rates()`，算的是"策略选出的票，之后第 N 天涨了多少"——没有持仓、没有资金曲线、没有手续费滑点、连买入价都用信号日收盘价顶替。它是**前瞻收益率标注器**，不是回测引擎。

> 结论：**手上确实一行回测代码都没有，从 0 写是必须的**。不过它有个用处——当对账基准（见第七节测试 10）。

**② 现有代码里有个正在生效的 bug**

实测对比了三代 K 线缓存：

| 缓存 | 数据源 | 复权 | 覆盖 |
|---|---|---|---|
| `klines_cache/` | 东财 | 前复权 | 123 只 |
| `klines_cache_v2/` | 腾讯 | 前复权 | 191 只 |
| **`klines_v3/`** | **新浪** | **不复权（原始价）** | **3430 只** |

实测同一只票（000403）2024-01-02 收盘价：东财前复权 20.78 vs 新浪 27.71，**差 25%**；到 2026-09-08 两者精确收敛到 1.000。这正是"前复权锚定最新价"的特征——说明新浪源给的是不复权的原始价。

问题在于 **`score_pool.py:7` 用的正是 `klines_v3`**（而且它是唯一覆盖全市场的缓存）。它 `:41-47` 的「红肥绿瘦」评分直接吃 `p_change`，而 `p_change` 是从**未复权**的 `close` 算出来的。

> **后果**：每只票除权除息那天，未复权价会出现假跳空（10 送 10，股价从 20 变 10），`p_change` 瞬间 -50%。这些假跌停会污染评分，让好票被误杀。历史段偏差最大到 25%，换算成日线就是好几个假跌停。
>
> 不是紧急故障，但意味着 **`scored.csv` 里的评分在除权股上不可信**。新平台的数据层建好后可以重算。

## 二、6 个关键设计决策

前 5 条决定了引擎可不可信（**回测不准的根源通常不在策略，而在地基**），第 6 条决定了收益能有多高。

### 决策 1：策略接口是「横截面」而不是「单标的」

现有策略全是**选股逻辑**——输入一只股票的历史，输出"这只票符不符合条件"。这是横截面策略，不是单标的择时。

instock 的策略签名（`stock/instock/core/strategy/enter.py:16`）：

```python
def check(code_name, data, date=None, threshold=60) -> bool
# code_name 是三元组 (date, code, name)，data 是日期升序的 DataFrame
```

**值得抄的地方**：

1. **纯函数** —— 无状态、可组合。`breakthrough_platform.py:37` 内部直接调用 `enter.check_volume(..., date=突破日)`，`parking_apron.py:33` 调用 `turtle_trade.check_enter(...)`。**策略调策略是免费的**，这个性质要保住。
2. **显式传 `date` 做时点截断** —— 每个策略开头都是 `data = data.loc[data['date'] <= end_date]`。防未来函数的思路天然就在里面。

**但返回值要升级**：从 `bool`（选不选）升级为**目标权重**。

```python
class Strategy:
    def on_bar(self, ctx, dt, bars) -> dict[str, float]:
        """返回目标持仓 {股票代码: 权重}。引擎负责下单。"""
```

**而不是** `buy()/sell()`。策略只表达"我想要什么仓位"，不碰下单细节——同一份策略代码将来换实盘只改引擎。

> **要避开的坑**：instock 的策略**就地修改了传入的 `data`**（`data.loc[:, 'ma60'] = ...`），导致调用方必须传副本——`breakthrough_platform.py:18` 和 `parking_apron.py:16` 只好写 `origin_data = data` 再自己 copy，而 `low_atr.py:19`、`turtle_trade.py:21` 漏了 copy，是 SettingWithCopy 隐患。
> **新项目约定**：策略不得修改输入，指标由上层算好注入。

### 决策 2：存「原始价 + 复权因子」，不直接存复权价

| | 前复权 | 后复权 |
|---|---|---|
| 基准 | 最新价（**会变**） | 上市首日（永不变） |
| 历史 bar 价格 | **每次除权都要重算** | **永远不变** |

```
前复权价(t) = 原始价(t) × 复权因子(t) ÷ 复权因子(今天)
```

分母里的"今天"会走。所以**前复权是拿未来的除权信息去改历史价格**，正式名称 Point-in-Time 偏差。同一份数据今天跑和一年后跑结果不一样，回测不可复现。

**更好的做法是存因子，不存结果价**：

```
data/daily/{symbol}.parquet
  date, open, high, low, close, volume, amount, ...   ← 全部原始价，永不重算
data/meta/adj_factor.parquet
  symbol, date, adj_factor                            ← 复权因子单独一张表
```

价值：

1. 原始价**永远不需要重算**，缓存不会静默过期
2. 需要后复权价时现算：`close × adj_factor`
3. **涨跌停判断、成交金额计算必须用原始价**——涨跌停是按原始价的 ±10% 定的，用复权价算会错

**复权因子从哪来——不用额外接口，能自己推**

东财 K 线里的 `涨跌幅` 和 `涨跌额` 是基于**除权后参考前收**计算的。所以：

```
除权参考前收 pre_close_ref = 收盘价 − 涨跌额
复权因子日变化 r_t = (1 + 涨跌幅/100) ÷ (收盘价_t ÷ 收盘价_{t-1})
累计复权因子 cumfactor_t = Π r_s        →    后复权价 = 收盘价_t × cumfactor_t
```

这意味着**不需要额外接口就能拿到复权因子和精确的涨跌停基准价**。停牌日东财会缺行，跨缺口的比值公式依然成立（因为用的是上一根 bar 的收盘价）。

**取价规则**（写死进代码，不要临场决定）：

| 用途 | 用什么价 |
|---|---|
| 算信号（均线/MACD/RSI/动量/突破） | **后复权价** |
| 判涨跌停、涨跌停基准 | **原始价 + 除权参考前收** |
| 成交价合法性校验 | **原始价**（`[low, high]` 是原始价区间） |
| 成交金额、佣金、印花税 | **原始价**（税费按真实成交额） |
| 100 股取整 | **原始价** |
| 持仓市值 | 原始价 × 真实股数（与券商对账单口径一致） |
| 净值 | `现金 + Σ 持仓市值` |
| 收益率 | 由净值序列导出，不单独取价 |
| **追赶判据**（`成交价 ≤ 信号日收盘 ×1.03`） | **原始价**（决策 5——这里最容易被漏掉，除权日 raw/adj 可差 25%） |

**防混用的工程手段：把口径钉死在 API 上**

```python
bars.raw.close      # 原始价（int32，单位分）—— 成交/涨跌停/取整/费用
bars.adj.close      # 后复权价（float32）—— 仅信号
# 故意不提供 bars.close，让"混用"从"靠纪律"变成"编译期不可能"
```

> 混用会**静默出错**。真实案例：用前复权价算信号、后复权价算绩效，敞口漂 0.3%，120 个交易日累积偏离 17%，年化 22% 被吃成 6%。

**三处最容易导致净值跳变的地方**：

1. **除权除息日** —— 用原始价估值但**不处理分红送股**的话，除息日会凭空出现 1%~4% 假跌幅，10 送 10 直接腰斩。**这是最经典、最容易被误读成"策略回撤"的静默错误**，年化高股息组合能凭空少 2%~4%。
2. **停牌** —— 估值价用**前向填充的 `last_valid_price`**，绝不能是 NaN（NAV 变 NaN，整条净值序列静默报废）或 0（假暴跌）。同时可交易性单独标记为 False。
3. **退市** —— 不能靠"从面板里消失"处理。持仓票退市时若直接从面板消失，`qty` 还在、价格变 NaN → NAV 静默崩掉或静默保住。必须显式标记，走 `forced_exit`；实在卖不掉的，剩余市值记为 0 并**在报告里单列为损失**。

### 决策 3：信号日 ≠ 成交日（硬性偏移一天）

策略在 T 日收盘后产生信号，但 T 日收盘那一刻**买不进去**。引擎必须强制：**订单最早在下一个 bar 成交**。

这条写反了不会报错，只会静默吐出错误绩效——是"静默失败"，最难查。

**低频选股最常用的月末调仓，日历语义要说清**：

| 概念 | 定义 | 坑 |
|---|---|---|
| **调仓信号日** | 每月**最后一个交易日** | ≠ "每月最后一天"。必须跳过周末和节假日 |
| **成交日** | 信号日的**下一个交易日** | 通常是下月第一个交易日 |
| **调仓频率** | 引擎参数（周频/双周/月频） | 策略每天返回目标也没关系，**引擎只在调仓日行动** |

> "每月最后一个交易日"和"每月最后一天"在 4 月、10 月、春节所在的月份都会差好几天。日历模块要提供 `is_month_end_trading_day()` 这种语义化接口，而不是让策略自己判断。

### 决策 4：T+1 / 涨跌停 / 停牌三件套必须建模

- **T+1**：当日买入当日不可卖。实现要点：`available = total − 当日买入`，必须在**日初复位**（`qty_bought_today` 在 `unlock_all()` 里清零），不能靠日终赋值
- **涨跌停**：见下方
- **停牌**：`volume == 0` 或当天无 bar → 跳过，**不要用填充值**

**涨跌停的两处细节（都会静默出错）**：

**① 判定要用"封死"语义，不是"收盘价 ±10%"**

```
买不进：low  >= 涨停价 − eps     # 全天封死涨停
卖不出：high <= 跌停价 + eps     # 全天封死跌停
```

用"收盘价 ±10%"太粗：会把**盘中触板但收盘回落**的票误判为不可交易（实际可以成交），也会在除权日误判。

**② 涨跌停价必须用整数分 + 四舍五入（HALF_UP），不能用 Python 内置 `round`**

```python
def limit_up_cents(pre_close_cents: int, pct_bp: int) -> int:   # pct_bp: 1000=10%, 500=ST 5%
    return (pre_close_cents * (10000 + pct_bp) + 5000) // 10000
```

> 内置 `round(1.265, 2)` 因为二进制浮点 + 银行家舍入会得到 `1.26`，而交易所规则是 `1.27`。这个差异会改变"哪些日子算涨停"→ 改变成交 → 改变全部收益。**典型静默错误，极难发现。**

**涨跌停基准价从哪来**：用**除权参考前收**，而不是昨收。东财 K 线里 `涨跌额` 字段直接给了：`除权参考前收 = 收盘价 − 涨跌额`。

### 决策 5：目标权重 → 实际订单

**先破除一个错误抽象**：现实里 A 股委托是当日有效、收盘自动撤单。但我们的模型不是"一笔笔委托"，而是**目标权重组合**。所以正确的抽象不是"挂单队列 + 有效期"，而是：

> **持久化的目标组合 + 每日从「目标 − 当前持仓」重新推导 + 追赶上限 + 放弃集合**

为什么不能用"挂单队列 + 有效期"：

- 一个 3 天有效期的买单，到第 3 天可能**已经不再是策略想要的票**了。策略在 T+3 已把它剔除，队列却还在买 → **静默买入不该买的票**，最难查的一类 bug
- 反过来，给"已卖出的票"留挂单会重复卖
- 一只票连续 10 个涨停（重组/摘帽行情），队列会一路追到第 10 天以最高价接盘

**具体策略**：

| 情形 | 策略 |
|---|---|
| **卖出**（减仓/清仓） | 每日重试，**无有效期**。本来就持有，不存在追高风险；卖不掉（跌停/停牌）就继续持有，下个调仓日重新推导 |
| **强制清仓**（退市/ST/剔除出池） | 单独列 `forced_exit`，**无有效期、无追赶上限**，超过 N 天未成交要**告警**——说明回测里有你实际逃不掉的仓位，必须显式呈现而不是偷偷留着 |
| **买入** | 追赶上限 `max_chase_days = 3`，且**仅在 成交价 ≤ 信号日 `raw.close` ×(1+3%)** 时才追。超限即放弃，进 `give_up` 集合，**该权重留作现金**，不重新分配给其他票 |
| **放弃后的现金** | 留现金。真实账户里你确实买不到，现金拖累是真实的；按比例分给其他名字会人为放大集中度，制造回测里不存在的收益 |

`give_up` 集合在下次调仓日**整体清空**（因为目标变了）。

**追赶判据的价格口径（必须钉死）**：用 `raw.close`，**不是 `adj.close`**。

这是决策 2「raw/adj 不混用」的边界，不能在这里破口——除权日前后的票 raw 与 adj 可能差 25%（见 1.1 的实测），用错价会让「追不追」的判断完全失真，而且**不报错**。

**`分批建仓` 与 `max_chase_days` 的关系（原方案含糊，这里定死）**：

| 情形 | 算不算「追赶」 |
|---|---|
| 分批建仓的**后续批次**（第 2、3 批按计划推迟） | **不算**。这是策略的主动设计，不是追涨 |
| **同一批次内部**，目标已产生但当天没成交 | **算**。受 `max_chase_days = 3` 约束 |

实现上：买入意图带 `batch_idx` 字段，`chase_days_used` 按 `(symbol, batch_idx)` 计数——即**每批各自有独立的 3 天追赶额度**。

> 不这么写会出现一个荒谬结果：第 3 批因为前 2 批占满了追赶额度而被直接放弃——**该买的票没买，且不报警**。

**订单推导（信号日收盘，只产出意图）**：

```
equity  = T 日收盘 NAV
目标市值 = weight × equity
目标股数 = 目标市值 / 价  →  向下取整到 100 的整数倍
差额     = 目标股数 − 当前持仓股数
```

**卖出股数规则**（容易漏）：A 股要求卖出余额不足 100 股的部分**一次性申报卖出**。所以：
- **清仓** → 允许零股
- **减仓** → 必须整手

**成交日撮合（先卖、后买、按优先级分配现金）**：

```
A. 先卖
   for 每笔卖出（按数量降序）:
       if 跌停封死 / 停牌 / 无 bar → 记拒绝原因，跳过
       qty = min(qty, available_qty)          # T+1 约束
       assert low ≤ 成交价 ≤ high             # 价格区间断言
       现金 += 成交额 − 费用

B. 再买 —— 先按比例缩放，再按优先级逐手填
   budget = 可用现金 − 最低留存
   缩放系数 s = min(1, budget / 所需总额)
   计划股数 = int(原股数 × s) // 100 * 100
   for 每笔买入（按金额降序）:
       if 涨停封死 / 停牌 → 记拒绝原因，跳过
       while 买不起: qty -= 100               # 逐手退让
       成交
```

**为什么要"比例缩放 + 逐手填充"两步，而不是二选一**：

- **纯按优先级**（大权重先吃饱）：现金不足时头部票满配、尾部票颗粒无收 = 给策略最大的那几个赌注做了系统性加权，**扭曲了策略本意**
- **纯按比例**：小额账户下每只票都缩到不足 1 手，**什么都买不到**
- **组合**：比例缩放保持策略的相对下注结构，逐手填充只解决 100 股不可分割的零头，跟踪误差最小

### 补充：账户规模 ↔ 持仓只数必须匹配（低频选股的实际约束）

这条不是技术问题，是**数学问题**，而且在 P4 设计持仓规则时会直接卡住你。

`min_trade_amount` 建议 5000 元（见下一节的理由）。但如果：

```
账户 10 万 ÷ 持仓 30 只 = 每只 3333 元   ← 低于 5000 元门槛
```

结果就是**大量股票根本买不进去**。而且 3333 元按 10 元/股只能买 300 股（3 手），**取整误差就有 3%**。

| 账户规模 | 合理持仓数 | 每只金额 |
|---|---|---|
| 10 万 | 10~15 只 | 7000~10000 |
| 50 万 | 20~30 只 | 17000~25000 |
| 100 万+ | 30~50 只 | 20000~33000 |

> **持有 50 只票、10 万本金，是做不了的。** 要么提高单只金额（减少持仓数），要么降低 `min_trade_amount` 但接受更高的成本占比。这个取舍要在策略参数里显式体现，不能靠引擎默默处理。

### 补充：换手抑制要四层，单靠最小金额不够

1. **调仓频率门控（收益最大的一层）**——引擎控制周频/月频。策略每天返回目标也没关系，引擎只在调仓日行动。**日频调仓在 A 股成本下几乎必死。**
2. **权重带（no-trade band）**——仅当 `|w目标 − w当前| > 1%` 才交易；**触发后交易到目标值，不是交易到带宽边缘**（回到边缘会让持仓钉在边缘、下次立刻又触发）

   > **⚠️ 这一层在最常见的账户规模下会自动失效**。实际触发门槛应取 `max(带宽金额, min_trade_amount)`：
   >
   > | 账户 | 持仓数 | 每只金额 | 1% 带宽 = | 实际门槛由谁定 |
   > |---|---|---|---|---|
   > | 10 万 | 10 只 | 1 万 | **100 元** | 5000 元 → **最小金额主导** |
   > | 50 万 | 25 只 | 2 万 | 200 元 | 5000 元 → **最小金额主导** |
   > | 100 万 | 30 只 | 3.3 万 | 330 元 | 5000 元 → **最小金额主导** |
   > | 1000 万 | 40 只 | 25 万 | 2500 元 | 5000 元 → 仍是**最小金额主导** |
   > | 1 亿 | 50 只 | 200 万 | 2 万元 | **带宽才终于主导** |
   >
   > 原因是算术性的：**A 股最低 5 元佣金推出 5000 元门槛，而「单只金额的 1%」要超过 5000 元，需要单只金额 > 50 万**，即账户规模在千万到亿这个量级。
   >
   > 结论：**别把「四层换手抑制」当成四层都在起作用**。对本平台的目标场景，真正生效的是**第 1 层（调仓频率门控）和第 3 层（最小交易金额）**，第 2 层可以留着但不要指望它。
   > 这个 `max()` 要写进 `order.py` 的显式规则，不能靠引擎默默取——否则你调 `band=1%` 到 `2%` 会发现结果**完全没变**，然后花半天找 bug。
3. **最小交易金额（针对整手噪声）**——建议 **5000 元**起。量化理由：佣金万 2.5 但**最低 5 元**，3000 元的单边佣金就是 5 元 = 万 16.7，双边加印花税往返成本约 0.35%+。**这个数字和最低 5 元佣金直接挂钩，别凭感觉设。**
4. **同标的净额化**——单次调仓内绝不同时买卖同一只票（先算净 delta 再分类）

**再加两道可信度护栏**（这是防错，不是省成本）：
- **单次调仓换手率上限**（如权益的 60%）——超过就告警并降级为按比例缩放，防止权重计算 bug 导致"全清全买"而你没发现
- **成本占比报告**——把「累计费用 / 累计毛利」打进结果。**成本吃掉 50% 以上收益，这个策略在实盘就没有意义。**

### 决策 6：组合构建是独立的一层

策略只负责「选哪些票、给什么分」；**「每只票配多少权重」应该剥出来单独做。**

**为什么值得单独一层**：

- 同一个选股逻辑，换不同的权重方案，**收益差别可能比换因子还大**
- 权重方案可复用——换策略不用重写
- **这是提升收益性价比最高的地方**，比调选股因子还高

**四种组合构建方法**：

| 方法 | 说明 | 适用 |
|---|---|---|
| **等权** | 选 30 只，每只 3.33% | 最简单，也最难被打败 |
| **因子加权** | 按因子值大小分配权重 | 因子单调性好时有效 |
| **波动率倒数** | 波动小的多配点 | 降波动、提升夏普 |
| **风险平价** | 让每只票贡献相同的风险 | 更进阶 |

**进阶约束**（后加）：行业上限、单票上限、换手上限。这些做在组合构建层，**跟选股逻辑解耦**。

**持有期规则**（同属这一层）：

| 规则 | 作用 |
|---|---|
| **最大持有期** | 一只票最多持有 N 个月，到期强制卖出——防止"僵尸持仓"长期占着仓位 |
| **止盈止损** | 涨了 50% 减半、跌了 20% 清掉 |
| **分批建仓** | 选出的票分 2~3 天买完，摊平成本 |

> 这三条跟 `forced_exit`（退市/ST 强制清仓）是**两回事**：`forced_exit` 是**被动**的合规卖出，这些是**主动**的策略规则。引擎要都能支持。

### 3.1 第 2 层：回测引擎（心脏）

```python
for i, dt in enumerate(calendar):
    bars = portal.day(i)                       # T 日切片

    # 1) 日初解锁（T+1）：昨日买入的今日可卖
    #    ★ 必须在 fill_pending 之前——清掉的是「昨天买的」
    acct.unlock_all()                          # qty_bought_today = 0

    # 2) 撮合：成交 T-1 收盘生成的计划，用 T 日真实价和真实现金
    broker.fill_pending(dt, bars, acct)        # 今日买入 → qty_bought_today += qty

    # 3) 结算校验
    acct.assert_invariants()                   # 现金≥0、qty≥0、available≤total

    # 4) 每日风控路径（与调仓日无关，每个交易日都跑）★ 原方案缺这一段
    ctx = Context(portal, i, acct, calendar)
    exits  = holding.check_daily(ctx, bars)       # 止盈止损 / 最大持有期到期
    forced = risk.check_forced_exit(acct, bars)   # 退市/ST：无上限，超 N 天告警
    plan_risk = derive_plan(exits + forced, acct, ctx, source="risk")

    # 5) 估值：T 日收盘
    nav = acct.mark_to_market(i, bars)
    recorder.record(dt, nav, acct, broker)

    # 6) 收盘后出信号（策略只能看 ≤ T 的数据；此时 nav 已是 T 日收盘）
    plan_rebal = None
    if calendar.is_rebalance_day(dt):
        picks   = strategy.on_bar(ctx, dt, bars)      # 选出哪些票、给什么分
        targets = portfolio.build(picks, ctx)         # 组合构建：算出权重（决策 6）
        targets = risk.check_targets(targets, ctx)    # 事前风控
        plan_rebal = derive_plan(targets, acct, ctx, source="rebalance")
        holding.reset_batches(targets)                # 分批建仓进度按新目标重置

    # 7) 合并意图 → 明日待成交队列
    #    plan_risk 只能「减仓/清仓」，不能加仓；冲突时以 plan_rebal 为准
    broker.queue(merge_plans(plan_risk, plan_rebal))
```

> **⚠️ 三处顺序/结构不能改**：
>
> **① `unlock_all()` 必须在 `fill_pending()` 之前。**
> 写反了**不会报错**：`fill_pending` 先把今日买入记进 `qty_bought_today`，紧接着的 `unlock_all()` 把它清零 → **当日买入当日即可卖**，T+1 被静默绕过。净值偏高，而且只有在「当天买、当天卖」的策略上才看得出来，极难发现。
> 语义记法：`unlock_all()` 解锁的是**昨日及更早**的买入，所以它必须跑在今日撮合**之前**。
>
> **② `submit → fill → mark` 是错的。**
> `submit` 执行时，T 日该成交的单子**还没扣款**，所以策略看到的是 T-1 的、且未扣除当日成交的现金 → **超额下单** → 到 T+1 现金不足，要么静默少买（权重不达标）、要么现金穿负。
> 关键原则：**定量发生在成交日，不发生在信号日**。信号日只记录"想做什么"，钱在成交日用真实价格和真实现金算。
>
> **③ 为什么必须有「每日风控路径」（步骤 4）。**
> 原方案只在调仓日调用策略，但决策 6 的**止盈止损**、**最大持有期**，以及 `forced_exit`，触发日都**不是调仓日**——它们必须逐日检查。缺了这条路径，这三类规则要么实现不了，要么会被硬塞进 `strategy.on_bar` 里，那就污染了横截面接口（决策 1）。
> 约束：`plan_risk` 只允许产生**减仓/清仓**意图，不能加仓；与 `plan_rebal` 冲突时以调仓日目标为准。

**防未来函数的机制**：策略拿不到全量 DataFrame，只能通过 `ctx` 的访问器取值，而访问器内部硬编码只返回 `index <= current_index` 的数据。策略**物理上够不着**未来数据。

**额外一道事后校验**：`risk.verify_post_trade(acct, i)`。涨停跳空可能让某只票被动超配，这个要能检测到（至少记日志）。

### 3.2 第 1 层：数据层

统一 schema（列名固定，全 snake_case）：

```
data/daily/{symbol}.parquet    ← 原始价，永不复权重算
  date, open, high, low, close, volume, amount, turnover,
  is_suspended, limit_up, limit_down

data/meta/adj_factor.parquet   ← 复权因子单独一张表
  symbol, date, adj_factor

data/meta/trading_calendar.parquet, symbols.parquet   ← 含已退市股票
```

> 命名不统一是当前代码里最烦人的问题——"涨跌幅"有 `CHANGE_RATE` / `change_rate` / `p_change` 三个名字，"量比"的 `VOLUME_RATIO`（官方量比）和 `vol_ratio20`（自算当日量/20 日均量）**根本不是一回事**。新项目从第一天就统一。

**数据规模**：沪深主板约 3100 只 × 8 年 ≈ 1960 个交易日 ≈ **608 万格**。宽表每字段 float32/int32 = **24 MB**，20 个字段 ≈ **487 MB**。8 GB 内存完全放得下。

**核心策略：启动时一次性把长表 pivot 成宽表常驻内存，循环内绝不再碰长表。**

**面板布局**（一字段一个二维数组，不用 DataFrame）：

```python
class Panel:
    dates: np.ndarray          # (T,) datetime64[D]  ← 转换路径见下方警告
    codes: list[str]           # (N,) 全体历史代码（含退市），固定顺序，永不重排
    col:   dict[str, int]      # code -> 列号

    # ---- 原始价：int32，单位「分」----
    o, h, l, c      : int32 (T,N)   # 缺失用哨兵
    pre_close_ref   : int32 (T,N)   # 除权参考前收 = close − 涨跌额
    limit_up/down   : int32 (T,N)
    last_valid_c    : int32 (T,N)   # 停牌日前向填充，估值专用

    # ---- 复权价：float32，仅信号 ----
    adj_c, adj_h, adj_l, adj_o : float32 (T,N)
    adj_factor      : float32 (T,N)

    # ---- 量额与标志 ----
    volume_shares   : int64 (T,N)   # 统一成「股」
    amount          : int64 (T,N)   # 元
    flags           : uint8 (T,N)   # bit0 上市 bit1 停牌 bit2 ST
                                    # bit3 退市整理 bit4 一字涨停 bit5 一字跌停
```

**⚠️ `dates` 转 `datetime64[D]` 的正确路径（实测踩坑）**

`DatetimeIndex.astype("datetime64[D]")` 会**直接抛 `TypeError: Cannot cast DatetimeIndex to dtype datetime64[D]`**。必须先落到纯 numpy：

```python
# ❌ 报错
di.astype("datetime64[D]")

# ✅ 三条可行路径
di.values.astype("datetime64[D]")        # 先取 .values（numpy）
np.array(di, dtype="datetime64[D]")
np.zeros(T, dtype="datetime64[D]")       # Panel 直接建，最常用
```

反向也有坑：`pd.DatetimeIndex([D数组])` 出来的是 **`datetime64[s]`**，不是 `[D]`。取舍见 3.2 归一化第 2 条。

**为什么原始价用「整数分」而不是 float32**：精度精确（复权价可能上万，float32 只有 7 位有效数字，分位会丢），且涨跌停算术变成整数运算，顺带消掉那类浮点陷阱。信号用的复权价只要相对精度，float32 够。

实测（pandas 3.0.6 / numpy 2.4.6）确认这两个选择都对：

| 检查 | 实测 | 结论 |
|---|---|---|
| `int32` 装「分」 | 上限 21,474,836 元 | 够（茅台高点 26 万分，20 万元也才 2000 万分） |
| `float32` 装复权价 | 2.6 万 → 误差 0.0000；12.3 万 → 0.0013；100 万 → 0.0100 | 信号够用；**绝不能拿来算钱** |

**NaN 语义**：缺失一律 NaN 或哨兵，**绝不用 0 填充**。`0` 会在 `rolling().mean()` 里静默拉低均值，是最常见的静默污染源。

### 3.2.1 指标预计算：让策略自己声明依赖

"策略是任意函数，引擎不知道它要什么指标"——干净解法是**让策略声明**。这是唯一既不限制策略灵活性、又能向量化的方案：

```python
class MyStrategy(Strategy):
    factors = {
        "ma20":        MA("adj_c", 20),
        "ma60":        MA("adj_c", 60),
        "vol_ratio20": Ratio(MA("volume_shares", 5), MA("volume_shares", 20)),
        "mom60":       ROC("adj_c", 60),
        "hh20":        RollingMax("adj_h", 20),
    }

    def on_bar(self, ctx, dt, bars):
        ma20  = ctx.factor("ma20")     # 返回当日横截面向量 (N,)
        score = ctx.cs_zscore("mom60") # 横截面 z-score，逐行算
        return pick_top(score, ma20, bars)
```

引擎侧：启动时对整块 `(T,N)` 面板向量化算一次并缓存到磁盘；`ctx.factor(name)` 退化成一次数组切片（微秒级）。

**性能差距（这不是优化，是可行性问题）**：

| 方案 | 单日成本 | 全程（1960 日） |
|---|---|---|
| 逐股 `ctx.history` + pandas rolling（3100 次/日） | ≈ 0.25 s | **8 分钟 ~ 1 小时** |
| 声明式因子 + 面板向量化 | ≈ 0.1–0.5 ms | **< 5 秒** |

**约 100 倍差距。** 所以 `ctx.history(code, n)` 只应作为**逃生口**（缠论、形态识别这类无法向量化的），并在文档里明确标注"此路径按 bar 重算，成本高"。`chan_theory.py` 就是典型的逃生口使用者。

**必须提前解决的两个前视偏差**：

1. **市值数据只有当期快照**。`snapshot.csv` 是 2026-09-10 的 `TOTAL_MARKET_CAP`/`FREE_CAP`。拿它去跑 2018 年的选股 = **前视偏差**，而且是小市值策略里最大的收益虚增来源（历史上小市值股票通过送转/增发使股本大幅变化）。要么从分红送配+股本变动表重建历史股本，要么**在小市值类因子上直接禁用当期快照**，只用 `amount`、`volume` 这类当日可得的量。
2. **ST 名单、行业分类也是当期快照**。现在代码里 `if "ST" in str(name)` 就是用今天的名字过滤 2018 年的股票。必须改成 as-of-date 的历史序列。

> **这两条的可执行性要提前确认，别到 P4 才发现做不了**：
>
> | 数据 | 能否拿到 as-of 历史序列 | 影响 |
> |---|---|---|
> | ST 名单 | ✅ 可从名称变更历史 + 交易所公告重建 | P0 补入 |
> | 历史股本 / 市值 | ⚠️ **需要额外的「股本变动」数据源**（东财股本结构接口） | 缺失则**市值中性化做不了** |
> | 行业分类 | ❌ 申万/中信历史分类免费几乎拿不到 | **行业中性化 / 行业上限建议降级为 P7 可选** |
>
> 结论：**P4 先只承诺「市值中性 + 流动性/上市天数过滤」**，行业相关的约束显式标记为"未做"，在报告里写清楚。这比做一个带前视偏差的行业中性化诚实得多。

### 3.3 P1 数据层的具体做法

**抓取——三个源都要接，做降级链**（这是刚需，不是可选）：

| 源 | 接口 | 复权参数 | volume 单位 |
|---|---|---|---|
| 东财（主） | `push2his.eastmoney.com/api/qt/stock/kline/get` | `fqt=1`前 / `2`后 / `0`不复权 | **手**，要 ×100 |
| 腾讯（备） | `web.ifzq.gtimg.cn/appstock/app/fqkline/get` | `qfq` | **手**，要 ×100 |
| 新浪（备） | `quotes.sina.cn/.../CN_MarketDataService.getKLineData` | **没有复权参数** | **股**，原生就是股 |

> 为什么要三个源：`run_all_v2.py:2` 注释写着"东财 push2his 被封时的替代源"，`fetch_pool_kline.py:2` 又换成了新浪。**东财会被封是常态**，降级链必须内建。
> 但**每个源的复权语义和 volume 单位不同**，降级时如果静默换口径，数据就废了。这三件事要固化成映射表，抓完立刻归一化。

**归一化**（踩过的坑，一条都不能省）：

1. **禁止按位置取列**。东财返回的是 `开盘,收盘,最高,最低`——**不是 OHLC**。instock 靠 `data.columns = [...]` 按位置重命名（`stockfetch.py:390`），接口一改字段就全错。必须按字段名显式映射。
2. **`date` 存 datetime64**，不要字符串。三代缓存的 `date` 全是 object。

   > **⚠️ 单位要显式定死，pandas 3.0 的默认变了。** 实测（pandas 3.0.6 / numpy 2.4.6）：
   >
   > | 环节 | 实际单位 |
   > |---|---|
   > | `pd.to_datetime([...])` 字符串解析 | **`datetime64[us]`**（不再是 `[ns]`） |
   > | `.astype("datetime64[D]")`（numpy 数组） | `datetime64[D]` |
   > | `pd.DatetimeIndex([D数组])` | **`datetime64[s]`**（自动变的，不报错） |
   > | `.as_unit("ns")` | `datetime64[ns]` |
   >
   > 四步四个单位，**每一步都不报错**。这就是 8.2 #17 的实际形态——比"str vs Timestamp"隐蔽得多。
   >
   > **规则**：在**加载层一次性 `as_unit()` 到统一单位**，之后**任何地方都不再依赖隐式转换**。选 `[ns]`（生态默认）或 `[us]`（pandas 3 默认）都行，但必须只选一个并写进 `normalize.py`。
3. **`code` 是 6 位字符串**，`dtype=str` + `zfill(6)`，否则 `1` 和 `300001` 会串。
4. **volume 统一成"股"**，并在 schema 里写死单位。
5. **按交易日历 reindex**。实测 400 只 `klines_v3` 里，最后一根 K 线分散在 09-08 / 09-09 / 09-10 三天——**没有对齐**。回测必须自己对齐时间轴，缺失的日子标记为停牌。

**存储**：`data/daily/{symbol}.parquet`（原始价）+ `data/meta/adj_factor.parquet`（复权因子）

- 按 symbol 分文件：增量更新只重写变化的那几只
- 每个 parquet 里塞一份 meta（`source / fetched_at / last_bar_date / bars`）——现在的 pickle 缓存**完全不知道是哪天抓的、什么复权、是否完整**
- Parquet 比 pickle 强在：列式存储、带 schema（列序变了会报错而不是静默出错）

**防半截数据**：抄 `run_all_v2.py:135` 的 `is_finalized()`——用**另一个独立接口**的 `MAX_TRADE_DATE` + `NEW_PRICE`（容差 0.5%）交叉校验最后一根 K 线。再配合"**盘中不落盘**"（`trade_time.py:121`）。

**交易日历**：instock 的做法（`core/crawling/trade_date_hist.py:306`）要跑 `py_mini_racer` 解一段加密 JS——**为了几行日期背一个带二进制引擎的依赖不值**。直接内置一份 CSV/JSON，每年更新一次即可。日期运算直接用 `stock/instock/lib/trade_time.py`（纯集合运算，零依赖）。

**必须包含已退市股票**，否则回测有幸存者偏差。

**读取**：`DataPortal` 启动时全量拼成内存宽表并缓存，回测过程中不再碰磁盘。

### 5.0 两个已定取舍

**① 分红送股：原始价记账 + 公司行为事件** ✅

账户全程用**真实价格 + 真实股数**记账，在除权日按公司行为调整：

```
现金分红  →  现金 += 每股派息 × 持股数
送股/转增 →  qty  += 每股送转 × 持股数
配股      →  按配股价和比例增加 qty，同时扣现金
```

好处：与券商对账单口径完全一致，最可信。代价：要多做一层数据。

数据源现成——`stock/instock/core/crawling/stock_fhps_em.py` 已有分红送配抓取。

**② 成交价：T+1 均价** ✅

```
成交价 = 当日成交额 ÷ 当日成交股数 = amount / volume_shares
```

数据里有这两个字段，直接算。比开盘价更接近真实成交分布，对大资金容量更稳健，一字板场景不会被高估。

> 两个字段的单位要小心：`amount` 是元，`volume_shares` 已统一成**股**。这个比值同时可以当数据校验断言用（见第八节 #5）。

**⚠️ 除零守卫（必须显式写，不能指望调用方先判停牌）**：

```python
def vwap_cents(amount: int, volume_shares: int) -> int | None:
    """成交均价（分）。停牌/无成交返回 None，由 broker 判为「不可交易」。"""
    if volume_shares <= 0 or amount <= 0:
        return None
    return round_half_up(amount * 100 / volume_shares)
```

停牌日 `volume == 0`，裸除法会抛 `ZeroDivisionError`；若走 numpy 则产出 `inf`/`nan` 并**静默污染 NAV**（这种最坏——第八节 #1 的"净值曲线异常平滑"就是这么来的）。
引擎里的停牌跳过逻辑（决策 4）和这个守卫是**两道独立的防线**，都要有：前者是业务判断，后者是数值安全。

### 5.1 P4 策略层：选哪三个策略

- **`Momentum`（N 日动量排序取前 K）**——横截面策略的样板

### 5.2 P5 报告：指标别贪多

先做这 8 个：

| 指标 | 为什么 |
|---|---|
| 累计收益 / 年化收益 | 最基本的 |

| 净值曲线 + 基准对比（**全收益指数**） | 图比数字直观。价格指数会系统性美化超额收益 |
| **拒绝原因分布** | 排查静默错误的主要工具 |

## 六、研报怎么做回测（以及你该抄什么）

券商金工研报（华泰、东吴、光大、中信建投等）是国内量化方法论的主要公开来源。它们做回测的方式和"写个策略看赚多少钱"有根本区别，值得单独说。

### 6.1 核心区别：研报测的是「因子」，不是「策略」

| | 常见做法 | 研报的做法 |
|---|---|---|
| 对象 | 一个策略 | 一个**因子** |
| 问题 | "这个策略赚多少钱" | "这个指标能不能**把股票排好序**" |
| 输出 | 一条净值曲线 | 一组**单调的**分组净值曲线 |

研报不关心买卖时点，它关心：**按某个指标给全市场股票排序，排在前面的股票是不是真的比排在后面的涨得好。**

### 6.2 研报的四步标准流程

**第 1 步：因子预处理**（标配，个人最容易漏）

```
原始因子值 → 去极值 → 标准化 → 中性化
```

- **去极值**：中位数 / MAD 法，把极端值拉回来
- **标准化**：z-score
- **中性化**：对市值、行业做回归，取残差

> **中性化为什么重要**：很多因子本质是**市值因子的马甲**。小市值股票既便宜、波动又大，你以为找到了"低估值因子"，其实买的就是小盘股。中性化就是把这个马甲扒掉，看它还有没有独立的信息。

**第 2 步：分层回测**（最经典，也最能说明问题）

按因子值把股票从高到低排序，**等分成 5 组或 10 组**，每组内部等权买入，每个截面期换一次仓。

看什么？**单调性** —— 各组净值曲线必须从高到低排得整整齐齐。如果 1、3、5 组比 2、4 组好，说明这个因子没有排序能力，直接扔掉。

同时测两种情况：**不计成本** 和 **单边千分之二**。换仓时点通常是"截面期下一个交易日按当日 VWAP 成交"。

**第 3 步：IC 分析**（量化"预测能力"）

**IC = 因子值和"下一期收益"的相关性**（秩相关，Spearman）

| 指标 | 含义 | 好的标准 |
|---|---|---|
| **IC 均值** | 平均预测能力 | 0.03~0.05 就算不错 |
| **ICIR** = IC均值 / IC标准差 | 稳定性 | > 0.5 算好 |
| **IC 胜率** | IC 为正的比例 | > 55% 算好 |

> IC 0.03 听起来小得可笑，但在几千只股票、按月调仓的场景下累积起来相当可观。**研报里的 IC 就是 0.0x 这个量级**——如果有人给你看 IC 0.3，基本是过拟合或者算错了。

**第 4 步：多空组合**

买第 1 组、卖最后一组。这是学术标准，但 **A 股融券很难做**，所以研报通常也同时报纯多头。**这一条你不必抄**（跟你的实际场景不符）。

### 6.3 一个关键数字：换手率是生死线

这条直接印证了决策 5 里的"调仓频率门控"：

| 年化换手率 | 结果 |
|---|---|
| **< 20%** | 净超额 ≈ 多头超额（成本几乎无感） |
| **> 40%** | 成本占比急剧上升，**净超额普遍转负** |

具体例子：`BIAS20` 因子换手率 77%，年化成本 **11.66%** → 净超额转负。而且 **10 日调仓的换手成本约为月频的 2 倍**。

**这解释了一个现象**：研报里绝大多数策略都是**月频调仓**。不是因为他们懒，是因为**日频在 A 股成本下几乎必死**。

### 6.4 研报回测的通病

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **未来函数** | 用当天收盘价决定当天买入；2024-04-01 就调用 2023 年年报（实际 4 月底才披露） |
| 2 | **幸存者偏差** | 直接用当前股票池。有实证：在标普 500 **最新**成分股上按波动率因子分组，会得出**相反结论** |
| 3 | **过拟合 / p-hacking** | 有人做过实验：**2565 种参数组合里轻松找到历史表现优异的**。试 5 个没 edge 的策略，至少一个 p<0.05 的概率是 22% |
| 4 | **成本假设过乐观** | 有的干脆不报成本，有的用早就过时的千三 |
| 5 | **不报容量** | 小市值因子实际装不下钱，回测里却按"无限流动性"算 |
| 6 | **样本太短** | 美国 EPS 因子 1987-1997 为正、1997-2000 为负、2000-2002 又为正——短期表现说明不了长期 |

> 还有一句该直说的：**研报是卖方研究**，目的是服务机构客户，金工组和自营/资管是分开的。研报的价值在于**方法论和思路**，不在于"照着买"。

### 6.5 该补进平台的（对应第五节路线图）

**好消息**：你已经定下的东西（完整成本模型、T+1、涨跌停封死、拒绝原因统计），**比相当一部分研报做得都严**——研报常有"不计成本"那一栏，你的引擎默认就要算成本。

建议补三样，都在 P4/P5 里，不难：

| 补什么 | 放哪 | 怎么实现 |
|---|---|---|
| **分层回测** | P5 报告 | 你的横截面策略天生就是一层；扩展成 5 层只是把 `pick_top()` 换成分组 |
| **IC / ICIR** | P5 报告 | 每个调仓日算一次因子值与下期收益的秩相关，累积成序列 |
| **因子中性化** | P4 因子层 | 至少做市值中性，否则策略很可能只是小盘股的马甲 |

**不用抄的**：多空组合（A 股融券难，跟实际场景不符）。

> 参考：[华泰证券·分层回测与多空组合构建](https://crm.htsc.com.cn/doc/2019/10750101/bf5935e6-742d-4713-9c1d-798d4dc807c1.pdf) · [东吴证券·换手率因子案例](https://bigdata-s3.wmcloud.com/researchreport/2023-05/d84d5daad5bdeb56247af8340297ef18.pdf) · [光大证券·多因子组合 Alpha 1.0](https://bigquant.com/wiki/doc/alpha-10-20170501-CQ5xmKwTOg) · [Failure Modes of Backtesting](https://www.longtailalpha.com/wp-content/uploads/2026/05/LTA-Failure-Modes-of-Backtesting.pdf)

## 七、怎么验证引擎是对的

回测引擎最可怕的是**静默出错**——跑得通、有结果、结果是错的。**下面这几条比任何功能都值钱**：

| # | 测试 | 验证什么 |
|---|---|---|
| 1 | **单票买入持有等价性**：单票、零成本、持有 N 日，引擎净值必须**逐日等于**该票的复权收益 | 同时验证分红处理、T+1、估值价 |
| 2 | **截断不变性**（最强的防未来函数测试）：把面板截断到第 T 日再跑一次，**前 T 日的净值序列必须与完整回测逐点相同** | 任何未来函数都会在这里暴露 |
| 3 | **现金守恒**：`Δ现金 == Σ卖出所得 − Σ买入支出 − Σ费用 + Σ分红`，每日校验 | 记账正确性 |
| 4 | **价格区间断言**：每笔成交价 ∈ `[low, high]` | 数据/逻辑错 |
| 5 | **权重往返一致性**：成交后重算权重，与目标权重之差必须能被「整手取整 + 不可交易 + 现金不足」**完全解释** | 有无法解释的差异 = 有 bug |
| 6 | **拒绝原因统计**：每天按 `涨停买不进/跌停卖不出/停牌/现金不足/整手归零/低于最小金额/追赶超限` 分类计数。**出现"原因不明的拒绝"即为 bug** | 排查静默错误的主要工具 |
| 7 | **买入持有对照**：第一天等权买入整个股票池、最后一天卖出，结果必须等于股票池的等权买入持有收益 | 撮合与结算 |
| 8 | **手工对照**：挑 2 只股票、5 个交易日，用 Excel 手算一遍净值，逐日比对到分 | 端到端 |
| 9 | **涨跌停验证**：构造连续一字涨停的票验证"买不进"；连续跌停验证"卖不出" | 决策 4 |
| 10 | **与 instock 对账**：跑一个"信号日买入、持有 N 天后卖出"的退化策略，应能复现 `rate_stats.get_rates()` 的数字。两条独立实现算出同一个数，说明收益口径没歪 | 收益口径 |

## 八、静默错误自检清单

回测引擎的 bug 分两种：**会崩的**（好查）和**不崩但算错的**（要命）。下面全属于后者——跑得通、不报错、结果就是错的。每写完一个功能，逐条对着查：

### 8.1 症状对照表

| # | 症状 | 检查方法 |
|---|---|---|
| 1 | 净值曲线**异常平滑** | 停牌日用了填充值或凭空多出收益 |
| 2 | 收益**高得不真实**（年化 >50%） | 十有八九是未来函数。先查成交价是不是用了信号日当天的价 |
| 3 | 净值**突然跳变** | 复权口径混用，或除权日没处理分红送股 |
| 4 | 信号日当天就有持仓变化 | 撮合循环写反了，订单没排队直接成交了 |
| 5 | 涨停板照样买进去了 | 涨跌停判断取错价，或用了"收盘价±10%"的粗判 |
| 6 | 资金**莫名其妙不够** | 卖出单受 T+1 的 `available_qty` 限制被静默跳过 |
| 7 | 交易笔数**爆炸** | 没做换手抑制，每天在买卖零头 |
| 8 | 某几只票**从头到尾没交易过** | 代码格式不统一（`1` vs `300001`） |

### 8.2 高危静默错误清单

| # | 漏洞 | 为什么静默 | 对策 |
|---|---|---|---|
| 1 | **生存者偏差**：universe = 今天的 3100 只 | 退市/被并购的票整体消失，回测看起来收益更高，不报错。2018 年主板约 1900 只，8 年间数百只退市 | universe 按**每个日期的实际存续代码**构建（含退市股） |
| 2 | **当期元数据回溯**：用今天的 ST 名单/行业/市值跑 2018 | 完全跑得通 | 全部改成 as-of-date 历史序列。现有 `run_strategy.py:191` 和 `score_pool.py:191` 的 `if "ST" in str(name)` 就是这个 bug |
| 3 | **分红送股未处理** | 见决策 2 末尾 | 原始价记账 + 公司行为事件 |
| 4 | **停牌日估值价** | 用 0 或 NaN | `last_valid_close` 预计算 |
| 5 | **成交量单位（手/股）混用** | 东财是**手**、新浪是**股**。两套缓存混用 → 100 倍误差 | 加载层统一成"股"，加断言 `low ≤ amount/volume ≤ high` |
| 6 | **印花税/过户费固定费率** | 2023-08-28 前后差一倍 | 时变费率表 |
| 7 | **涨跌停价用内置 `round`** | 银行家舍入 + 浮点 | 整数分 + HALF_UP |
| 8 | **涨停判定用收盘价 ±10%** | 漏掉盘中触板可成交、除权日误判 | 封死语义（`low ≥ 涨停价`） |
| 9 | **现金穿负不报错** | 静默少买或买到不存在的钱 | 每日 `assert_invariants`，`--strict` 直接抛异常 |
| 10 | **成交价不在 `[low, high]`** | 数据/逻辑错，但 NAV 照样算得出来 | 每次成交断言，异常即中断 |
| 11 | **调仓日 off-by-one** | 把"本月第一个交易日"的信号算到当日收盘 | 引擎显式提供 `signal_date` 与 `exec_date = 下一个交易日`，日历统一用整数位序 |
| 12 | **T+1 记账** | `available = total − 当日买入` 必须在**日初复位**，不能靠日终赋值 | `qty_bought_today` 在 `unlock_all()` 里清零 |
| 13 | **NaN 进权重** | `np.argsort` 把 NaN 排到末尾 → 静默入选/落选 | 排序前显式 `np.isfinite` 掩码 |
| 14 | **策略给不可交易的票赋权重** | 引擎静默持有现金，权重不达标 | 显式 drop 并计入拒绝统计 |
| 15 | **新上市/次新** | 首日涨停机制不同（首日 ±44%，之后 ±10%），60 日内波动异常 | 上市天数 < N 的票从池中剔除 |
| 16 | **基准选价格指数** | 沪深300 价格指数 vs **全收益**指数差约 2%/年，系统性美化超额收益 | 用全收益指数（如 H00300） |
| 17 | **日期类型混用 / 单位漂移** | ① str 与 Timestamp 比较走字典序，静默筛错；② **datetime64 单位在 pandas↔numpy 边界自动变**：`[us]`→(numpy)`[D]`→(pandas)`[s]`，四步四个单位且**每步都不报错**（pandas 3.0 实测） | 加载层一次性 `as_unit()` 到统一单位；引擎内用整数位序；**禁止依赖隐式转换** |
| 19 | **字符串 dtype 变化** | pandas 3.0 起字符串列默认是 `StringDtype(na_value=nan)`，**不再是 `object`**。任何 `if col.dtype == object` 的判断会静默失效，走进错误分支 | 判断字符串用 `pd.api.types.is_string_dtype(col)`，不要比 `object` |
| 20 | **链式赋值无法升级为异常** | `df[a][mask] = x` 在 CoW 下**不生效**，只发 `ChainedAssignmentError` **警告**；实测 `mode.chained_assignment="raise"` **设了也不抛**，所以没法靠配置强制失败 | 只能靠规范：**赋值一律用 `df.loc[mask, col] = x`**。P1 起加 code review 检查项 |
| 18 | **不可复现** | 前复权重写、无种子、无配置记录 | 存 `data_version_hash` + `config_hash`，与结果一同落盘 |

### 8.3 通用手段

每个调仓日打印 `日期 / 持仓数 / 可用资金 / 总资产 / 当日拒绝笔数`。

**总资产的每日变化必须能解释**——要么来自持仓涨跌，要么来自交易，要么来自分红，对不上就是有 bug。这一行日志能揪出上面一大半问题。
